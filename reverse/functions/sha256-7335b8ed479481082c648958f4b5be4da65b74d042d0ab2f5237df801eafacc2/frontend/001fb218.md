### TASK-0021 addition (E-0021-24)

The create path was read in full. On message 0x0B this allocates **0x860 bytes** from the pool
named `tEventTreeView` (string 0x002BA8F8), calls `FUN_00185568(0x2FC050)` to choose the tree and
hands both to FUN_001F96B8. The `0x2FC050` literal is the player profile's base address, which is
a fourth independent confirmation of it (see
`reverse/structures/.../memorycard/Profile_002FC050.md`), and it is what makes the tree follow the
mode the mode-select screen wrote rather than any value the host picks.

**Its registration was missing from the port, and that is why the event tree was unreachable.**
This class does not register through FUN_0016ADB0 like the other 37: it is reached by a tail call
to the sibling FUN_0016AD88 at 0x001FB860, whose operands are built at 0x001FB7F0..0x001FB830 --
`lui a1,0x2c` + `addiu a1,a1,-0x58e8` gives the class-name string 0x002BA718 ("View Event Tree"),
`lui a2,0x20` + `addiu a2,a2,-0x4de8` gives this function, and `lui a3,0x147f` +
`ori a3,a3,0x8a59` gives the document hash **0x147F8A59**, which is exactly FRONTB.BUN screen 39's
stored name hash. The row `{"View Event Tree", 0x147F8A59u, 0x001FB218u}` is now in
`src/game_core/port/frontend/frontendscreens/registry_0016adb0.cpp`.

Worth recording because it is easy to get wrong: a registration's document hash is the **screen's**
stored name hash, not `StringHash_002534A8` of the class name in the same row. The two differ here
-- the class name hashes to 0xFB14F36C -- because the class name and the authored document name
are different strings.
